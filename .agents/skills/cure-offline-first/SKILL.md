# Офлайн-работа Cure

## Требование продукта

Cure должно работать без интернета после первого успешного онлайн-входа
и подготовки локальных данных. Пользователь может закрыть приложение,
открыть его заново без сети, читать сохранённые данные и выполнять основные
операции создания, изменения и удаления. Изменения сохраняются локально
и синхронизируются с Convex после восстановления связи и подтверждения сессии.

Офлайн-поддержка — обязательное свойство новых функций приложения,
а не отдельный режим разработки. Установленные npm-пакеты сами по себе
не означают, что офлайн-работа реализована. Этот скилл задаёт требования;
при работе только над инструкциями не изменяй архитектуру приложения.

## Стек и границы

- Используй TanStack DB и `@tanstack/react-db` для локальных коллекций
  и реактивных запросов к данным приложения.
- Подключай Convex через `@tanstack/convex-db-collection`.
  Convex остаётся сервером синхронизации, авторизации и проверки операций.
- Сохраняй данные коллекций в постоянном браузерном хранилище, совместимом
  с установленной версией адаптера. Коллекция в памяти и кеш TanStack Query
  не заменяют такое хранилище. Не подменяй синхронизируемую коллекцию
  отдельной IndexedDB-коллекцией без определённого механизма синхронизации.
- Для сохраняемых между перезапусками изменений используй
  `@tanstack/offline-transactions` и Convex offline bridge.
  Адаптер коллекций не заменяет постоянную очередь исходящих операций.
- Сначала изучай установленную версию, её типы и документацию. В TanStack DB
  используются RC-пакеты; не переноси API другой версии без проверки.
  Композируй готовые API вместо собственной очереди, протокола синхронизации
  или второй копии коллекций в React state.
- Сохраняй текущие соглашения проекта: конфиги на TypeScript, импорты
  `@/...` от корня репозитория, Lingui для текста интерфейса.

## Чтение и изменение данных

В интерфейсе читай данные из локальных коллекций. При наличии сохранённых
данных старт страницы и работа с ними не должны ждать ответа Convex.
Отличай отсутствие локального набора от действительно пустого набора.
Не обещай доступность данных и файлов, которые ещё не загружались.
Для новой функции определяй, какие данные заранее сохраняются для офлайна.

Проводи поддерживаемые офлайн-записи через offline action/transaction.
Прямой `collection.insert/update/delete` с обычным обработчиком не гарантирует
запись в постоянную очередь. Видимое optimistic-изменение не доказывает,
что оно переживёт закрытие вкладки: подтверждай локальное сохранение
по документированному состоянию очереди. Не жди завершения серверной
отправки, чтобы разрешить пользователю продолжить локальную работу.

Сохраняй стабильными идентификаторы коллекций, их ключи в registry,
имена mutation functions и кодек очереди между перезапусками.
Для офлайн-создания записей используй стабильный клиентский UUID,
например `clientId`, который также хранится на сервере. Не выдавай
временную строку за серверный Convex `_id`.

## Доставка и конфликты

Передавай стабильный `idempotencyKey` из очереди в Convex mutation.
Проверяй ключ и выполняй запись результата в одной серверной транзакции
с изменением данных. Ограничивай ключ владельцем операции и проверяй
его права до возврата ранее сохранённого результата.
Повторная доставка после обрыва или перезапуска не должна дублировать запись.

Повторяй временные ошибки связи с ограничением частоты. Ошибки валидации
и окончательный отказ в доступе должны получать конечный статус,
а не бесконечно повторяться. Истёкшую сессию обрабатывай как необходимость
повторного входа: сохраняй ожидающую работу и возобновляй её для того же
пользователя после входа. Не показывай успех серверной синхронизации заранее.

Для конкурирующих правок выбирай явную политику по смыслу данных:
версионирование, слияние либо разрешение конфликта пользователем.
Не перезаписывай чужие изменения молча. Учитывай зависимые операции
«создать → изменить → удалить», несколько вкладок и смену лидера очереди.
Проверяй `isOfflineEnabled` и ошибки хранилища: запасной online-only путь
не должен незаметно выдавать себя за надёжное офлайн-сохранение.

## Авторизация и изоляция

Better Auth и Google сохраняются. Первый вход, повторная проверка
серверных прав и восстановление просроченной серверной сессии требуют сети.
Офлайн-доступ к ранее сохранённым данным — отдельное локальное состояние,
которое не выдаёт новых серверных прав. Разрешай его только для ранее
подтверждённого пользователя с подготовленным локальным рабочим пространством.

Не трактуй сетевую ошибку `getSession/getToken` как подтверждённый logout.
Не очищай данные или очередь только из-за отключения интернета.
Разделяй состояния «проверяем», «сессия подтверждена», «работаем офлайн
с локальными данными», «нужен повторный вход» и «пользователь вышел».

Изолируй коллекции, постоянное хранилище и очередь по пользователю,
а при необходимости — по workspace. При выходе или смене аккаунта
останавливай синхронизацию прежнего пользователя и закрывай доступ
к его локальным данным. Не отправляй его очередь под новой сессией.
Определи явное поведение для неотправленных изменений при выходе;
не удаляй их молча. Очистки одного `QueryClient` недостаточно.
Офлайн-выход должен блокировать локальный доступ; серверный отзыв сессии
нельзя считать выполненным, пока сервер его не подтвердил.

Google client secret, Better Auth secret и прочие серверные секреты
не должны попадать в клиентские коллекции, кеш Service Worker или бандл.
Все воспроизводимые операции повторно проверяются сервером Convex.

## Запуск приложения без сети и SSR

Настрой Service Worker и кеширование оболочки приложения, необходимых
маршрутов, JS/CSS, переводов и используемых локальных ресурсов.
Офлайн-перезагрузка и прямое открытие поддерживаемого маршрута должны
показывать приложение с локальными данными. Проверяй собранную production-
версию: успешная работа уже открытой dev-вкладки этого не доказывает.

Сохраняй SSR для онлайн-запросов. Браузерное хранилище и offline executor
создавай только на клиенте; серверные клиенты и данные изолируй по запросу.
Для холодного офлайн-запуска предусматривай клиентскую загрузку локальных
данных: недоступный серверный loader или `createServerFn` не должен
блокировать всё приложение. Не кешируй персонализированный SSR HTML
и ответы `/api/auth/*` как общую оболочку для всех пользователей.

Обновление Service Worker, схемы хранилища или версии приложения
не должно терять постоянную очередь. Проверяй миграции сохранённых данных.
Статус сети определяй также по результатам реальных попыток синхронизации:
`navigator.onLine` не гарантирует доступность Convex.

Функции, зависящие от внешнего сервиса, например облачного AI, должны явно
показывать недоступность без сети. Сохраняй ввод и черновики локально;
если предусмотрена отложенная отправка, делай её статус понятным.
Не изображай локальное выполнение внешнего сервиса.

## Проверка изменений

Для затронутых сценариев проверяй наблюдаемое поведение:

1. Онлайн-вход и загрузка данных → отключение сети → чтение и правки.
2. Закрытие приложения → повторный запуск без сети: данные и очередь сохранены.
3. Возвращение сети: изменения доставлены без дублей; получены серверные обновления.
4. Обрыв после записи на сервер, но до ответа: повтор не дублирует операцию.
5. Истечение сессии, повторный вход тем же пользователем и смена аккаунта:
   чужие данные и очередь не становятся доступны.
6. Несколько вкладок, конфликт правок, недоступное хранилище и обновление
   приложения: нет ложного сообщения об успешном сохранении или потери очереди.

Автоматизируй относящиеся к изменению сценарии, включая перезапуск браузерного
контекста и сетевые отказы. Не считай отсутствие сети внутри одного mocked
запроса достаточной проверкой офлайн-перезапуска. Выполняй проверки с учётом
ограничений запуска и тестирования из `AGENTS.md`.
В отчёте указывай, что проверено, какие данные доступны офлайн и что ещё
требует сети. Не называй приложение готовым к офлайн-работе только на основании
установки зависимостей или создания этого скилла.
