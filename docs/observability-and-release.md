# CURE: наблюдаемость, эксперименты и релизы

Дата проверки источников: **28 октября 2026 года**.
Статус: **архитектурный план**. Инструменты, интеграции, hooks и CI из документа ещё не настроены; проверки не выполнялись.

## 1. Решение и границы

Для единого рабочего места предлагается **Datadog**: Product Analytics, RUM, Error Tracking, APM, Logs, Synthetics, SLO, Feature Flags и Experiments.
OpenTelemetry используется для собственного SSR, фоновых обработчиков и интеграционных сервисов; Convex подключается через доступные платформенные интерфейсы.
Перед закупкой нужен пилот: доступность продуктов в выбранном Datadog site, договорные условия, регион обработки, retention и стоимость ожидаемого потока.
Одна платформа не означает один тариф: Product Analytics, replay, эксперименты и другие продукты имеют отдельные условия использования.

| Требование | Предлагаемый механизм | Проверенная граница |
|---|---|---|
| Воронки, пути, retention | Product Analytics | Использует те же Browser/Mobile SDK, что RUM; отдельный продукт |
| Браузерные ошибки и performance | RUM и Error Tracking | Видимость ограничена работой браузера, согласием и доставкой событий |
| Серверные traces, metrics, logs | OpenTelemetry → Collector/Agent → Datadog | Собственные процессы можно инструментировать; внутренности managed Convex не раскрываются автоматически |
| Внешняя доступность | API/browser synthetic journeys | Проверки из нескольких локаций, включая отдельные mobile/desktop сценарии |
| Контроль выкладки | Feature Flags, progressive rollout, canary | APM guardrails обозначены Preview; требуется проверка доступности |
| Продуктовый A/B | Experiments | Гипотеза, метрики, единица рандомизации, exposures и диагностика эксперимента |

Источники: [Product Analytics и RUM](https://docs.datadoghq.com/product_analytics/guide/rum_and_product_analytics/), [OTLP](https://docs.datadoghq.com/opentelemetry/setup/otlp_ingest/), [Synthetics](https://docs.datadoghq.com/api/latest/synthetics/), [Feature Flags](https://docs.datadoghq.com/feature_flags/), [Experiments](https://docs.datadoghq.com/experiments/plan_and_launch_experiments/).

## 2. Почему не выбирать PostHog автоматически

PostHog остаётся реальной альтернативой для продуктовой аналитики, feature flags, экспериментов, ошибок и replay.
Утверждение «у PostHog нет logs, metrics и distributed tracing» уже неверно: все три направления представлены в актуальной документации.
[Logs](https://posthog.com/docs/logs) и [distributed tracing](https://posthog.com/docs/distributed-tracing) принимают OpenTelemetry; собственный span API в [Node SDK](https://posthog.com/docs/libraries/node) обозначен experimental.
[Application Metrics](https://posthog.com/docs/metrics) находится в **open alpha**: параметры интеграции могут изменяться, retention alpha составляет 30 дней.
Поэтому Datadog выбран как исходный вариант для эксплуатационного контура со SLO и synthetics; это инженерная оценка зрелости нужного CURE набора функций.
Если бюджет делает Datadog неприемлемым, PostHog проверяется тем же пилотом на latency, доставку, alerting, retention и восстановление наблюдения после сбоя.
Переход на альтернативу должен сохранять измеряемые требования; наличие пунктов в каталоге продуктов само по себе их не подтверждает.

## 3. Три независимых вида записей

| Вид | Назначение | Источник истины |
|---|---|---|
| Техническая telemetry | Диагностика ошибок, задержек, ресурсов и доступности | Datadog; с известными ограничениями доставки |
| Подтверждённое бизнес-событие | Например, согласие сохранено или экспорт завершён | Серверная транзакция/зафиксированный результат операции |
| Медицинский аудит | Кто, когда, на каком основании получил доступ или изменил данные | Отдельный долговечный audit-контур с ограниченным доступом |

Клик «Подписать согласие» означает намерение пользователя. Событие `consent.signed` появляется только после успешного сохранения версии согласия сервером.
Если нужны надёжные бизнес-метрики, в той же транзакции создаётся outbox-запись; отдельный обработчик доставляет разрешённую проекцию события в аналитику.
Экспорт повторяется с устойчивым `event_id`, контрольной точкой и дедупликацией. Отдельно наблюдаются задержка доставки и необработанные записи.
Не следует обещать exactly-once доставку внешнему аналитическому сервису: проверяется идемпотентность при повторных отправках и подтверждениях.

## 4. Convex: обычные логи, audit и traces

[Log Streams](https://docs.convex.dev/production/integrations/log-streams/) требуют **Pro** и поддерживают Datadog, PostHog, Axiom и webhook.
Поток содержит сведения об исполнении функций, статусе, длительности, request ID, расходе ресурсов и operational-событиях.
Это **best-effort** доставка: записи могут теряться и дублироваться. Поток подходит для диагностики, но не как единственный медицинский журнал.

Для строгого read audit основной кандидат — [Convex Audit Logging](https://docs.convex.dev/production/integrations/audit-logging):

- `log.audit` требует **Enterprise**, dedicated deployment **D1024/D2048** и настроенный S3 bucket в собственном AWS account.
- Query-аудит создаётся при выдаче результата каждому subscriber, включая cache hits; динамические timestamp/IP/User-Agent обновляются при повторной выдаче.
- Commit функции ожидает сохранения audit-записи; доставка в S3 происходит с задержкой и имеет семантику **at least once**.
- Возможны записи о неуспешных транзакциях и OCC retries: audit-запись сама по себе не доказывает завершённую бизнес-операцию.
- Прямой `log.audit` в action не поддержан и приводит к ошибке; вызванные из action query/mutation используют свои audit-гарантии.
- Identity нужно явно включать из доверенного серверного контекста. Для scheduled операций actor передаётся сервером, а не берётся из пользовательского аргумента.
- `custom_audit` через обычный Log Stream предназначен для разработки и не получает долговечность S3-доставки.
- Подключение S3, дедупликация, retention, проверка доставки и ограничение доступа входят в отдельный эксплуатационный пилот.

Если Enterprise не выбран, чувствительные выдачи проектируются через контролируемый серверный путь с долговечным журналом выдачи.
Выдача grant не равна чтению данных; обычная subscription/query не должна обходить этот путь, если требуется строгий аудит каждого доступа.
Ограничения такого варианта документируются до подключения клиники. Нельзя обозначать его эквивалентом штатного query audit без проверки всех путей.

Convex Log Streams не создают полную distributed trace внутренних операций управляемой базы.
В собственных сервисах распространяется correlation ID; Convex request ID и безопасные метаданные связывают доступные записи с операцией.
Не добавляются сетевые exporters внутрь query/mutation ради имитации трассировки; используются поддерживаемые платформой механизмы.

## 5. Централизованная интеграция

Планируется один модуль `observability/`: настройка SDK, разрешённые event schemas, redaction, correlation и адаптеры границ приложения.
Прямые импорты vendor SDK вне этого модуля запрещаются lint-правилом. Это правило относится и к новым маршрутам.

| Граница | Что подключается централизованно |
|---|---|
| Router | Начало/окончание перехода, route template, mobile/desktop вариант |
| React | Root error boundary и контролируемое представление ошибки |
| Browser | Unhandled errors/rejections, ресурсы, Web Vitals |
| TanStack Query | Общие callbacks cache для операций, реально проходящих через Query |
| Convex client/server | Собственные границы вызовов и Log Streams; Query callbacks не покрывают их автоматически |
| SSR, API, коннекторы | Request middleware, OTel, структурированные ошибки и таймауты |
| PWA/worker | Отдельная точка инициализации и доставка разрешённых diagnostic events |

Семантические события определяются в одном каталоге: имя, версия, владелец, поля, источник подтверждения, retention и правила дедупликации.
Для UI-действия без серверной операции допустим один типизированный вызов или декларативная метка; автоматический сбор всех кликов не заменяет бизнес-смысл.
Ошибки связываются с release SHA и source maps; fingerprint и event ID предотвращают многократное отображение одной ошибки разных перехватчиков.
Потеря telemetry, переполнение очереди, отсутствие свежих данных и ошибки exporter сами имеют отдельные метрики и alert.

## 6. Минимизация данных

В product telemetry допускаются только согласованные поля: route template, operation, outcome, duration, release, locale, UI variant и псевдонимный субъект.
Высококардинальные user/request IDs не используются как labels метрик; для correlation они хранятся в подходящих событиях или traces с ограниченным доступом.
Исключаются медицинские значения, свободный текст, тела запросов, токены, имена, содержимое отчётов и сырые URL/query с идентификаторами.
Scrubbing выполняется до отправки: browser `beforeSend`, серверная сериализация по allowlist и Collector processors. Ingestion scanner — дополнительный контроль.
Session Replay на клинических страницах **выключен по умолчанию**. Для отдельно разрешённого использования задаётся явная маскировка и проверяется фактический payload.
Не включаются автоматические HTTP payloads и реальные пациентские данные в synthetic tests; тестовые организации и записи изолируются.
Регион, retention и доступ к медицинскому audit отличаются от продуктовой аналитики; согласие на исследование не считается автоматически согласием на analytics.
Проверки включают canary-значения чувствительных данных: они не должны попадать ни в browser events, ни в logs, traces, replay или AI telemetry.
Настройки предоставляет [Datadog RUM](https://docs.datadoghq.com/data_security/real_user_monitoring/); их корректное применение остаётся обязанностью CURE.

## 7. Измеримые цели доступности

**100% SLA и 100% видимость ошибок не принимаются как доказанное свойство архитектуры.** SLA фиксируется договором, SLO задаёт измеримую техническую цель.
Предлагаемый стартовый SLO доступности критических путей — **99,9% за 30 дней**; повышение до 99,95% рассматривается после эксплуатационного пилота.
Для time-based SLI это около 43,2 и 21,6 минуты бюджета соответственно; для request-based SLI бюджет измеряется долей неуспешных операций.
Критические пути: вход, чтение разрешённых данных, сохранение согласия, отзыв доступа и запуск/получение экспорта.
Ошибки инфраструктуры считаются неуспехом; ожидаемый отказ в доступе не маскируется под сбой и не исключает ошибочные запреты законному пользователю.

| SLI | План измерения и принятия цели |
|---|---|
| Доступность | Успех критического сценария плюс независимые synthetics из нужных регионов |
| Задержки | p95/p99 отдельно для чтения, записи, импорта, экспорта; границы фиксируются после baseline |
| Отзыв доступа | Новая выдача проверяет актуальное разрешение; задержка прекращения активных выдач измеряется отдельным тестом |
| Свежесть импорта | Время от получения исходного пакета до доступности нормализованных данных |
| Полнота контроля | У каждого критического сценария есть сигнал успеха/ошибки, владелец, alert и runbook |
| Здоровье telemetry | Последняя доставка, backlog, drops, дубли и отставание durable audit |

Alerting использует burn rate/error budget, несколько временных окон и маршрутизацию ответственному; при исчерпании бюджета ограничивается выпуск новых функций.
Нужны учения: сбой провайдера, истечение сессии, offline, exporter outage, восстановление очереди и потеря одного региона наблюдения.
RUM не видит все browser crashes, заблокированные запросы и offline события; synthetic checks дополняют, но не устраняют эти ограничения.
Основа настройки: [Datadog SLO](https://docs.datadoghq.com/service_level_objectives/) и [error-budget alerts](https://docs.datadoghq.com/service_level_objectives/error_budget/).

## 8. Продуктовые A/B и управление флагами

Для эксперимента обязательны: владелец, гипотеза, primary metric, guardrails, единица рандомизации, срок, целевая аудитория и правило принятия решения.
Вариант стабилен для одного субъекта; для совместных сценариев субъектом может быть организация или команда, чтобы участники не получали противоречивый процесс.
SSR определяет вариант и передаёт согласованный bootstrap клиенту; повторная независимая рандомизация после hydration недопустима.
Exposure фиксируется при фактическом использовании варианта; успешная бизнес-метрика поступает из подтверждённой серверной операции.
Проверяются sample ratio mismatch, пропуски, повторные exposures и загрязнение групп; «статистическая значимость» без условий эксперимента не означает готовность релиза.
У флага есть безопасное значение по умолчанию, владелец, дата удаления, история изменений и аварийное выключение.
Flags не выдают права доступа и не заменяют серверную авторизацию. Для offline и устаревшей конфигурации заранее задаётся политика доступности функции.
**Рандомизация клинического исследования — отдельная валидируемая подсистема протокола.** Продуктовый A/B SDK не распределяет пациентов по лечебным группам.
Источники: [настройка Experiments](https://docs.datadoghq.com/experiments/plan_and_launch_experiments/), [канареечные выкладки](https://docs.datadoghq.com/feature_flags/use_cases/progressive_rollouts/), [аудит изменений флагов](https://docs.datadoghq.com/account_management/audit_trail/events/).

## 9. Инструменты разработки и CI

| Задача | Выбор и ограничение |
|---|---|
| Lint | Rslint; проверить требуемые React/hooks/a11y/import rules и сторонние plugins на выбранной версии |
| Форматирование | Prettier; Rslint не объявляется formatter |
| Typecheck | Отдельный обязательный шаг; переход на Rslint `--type-check` после проверки эквивалентности проекту |
| Unit/component | Rstest с Node/jsdom либо браузерным режимом после пилота |
| Backend integration | Rstest как runner + настоящий изолированный local Convex backend, fixtures и cleanup |
| Mock backend | `convex-test` документирован с Vitest; совместимость с Rstest — отдельный spike, не готовая интеграция |
| Сквозные сценарии | Отдельный Playwright suite: SSR auth, роли, mobile/desktop routes, consent, export и offline |
| Анализ сборки | Rsdoctor только для Rspack-сборок; не заменяет runtime performance и не подключается автоматически к Vite |

[Rslint plugins](https://rslint.rs/config/plugins) поддерживают нативные правила и сторонние ESLint plugin objects; конкретное покрытие проверяется до удаления существующих проверок.
[Rstest Browser Mode](https://rstest.rs/guide/browser-testing/) использует Playwright и обозначен experimental; [coverage](https://rstest.rs/config/test/coverage) поддерживает Istanbul/V8 с ограничениями браузерных режимов.
Официальная настройка [convex-test](https://docs.convex.dev/testing/convex-test) использует Vitest и mock backend; она не подтверждает реальную семантику Convex production.
Базовые интеграционные тесты проверяют tenant isolation, согласия, истёкшие grants, OCC/retry, идемпотентность и subscriptions на [local backend](https://docs.convex.dev/testing/convex-backend). Локальный backend не даёт mock-контроля времени и сети: scheduler-тесты используют ограниченные реальные интервалы и отдельные тестовые зависимости; ожидаемое поведение облачных интеграций дополнительно проверяется в staging.
[Rsdoctor](https://www.rsdoctor.rs/guide/start/intro) применяется для анализа compilation/bundle там, где используется Rspack.

Native Git hooks задаются через `core.hooksPath`: pre-commit проверяет staged formatting/lint, commit-msg — Conventional Commits, pre-push — короткий набор проверок.
Hooks не являются барьером безопасности: их можно пропустить, поэтому обязательные проверки повторяются в GitHub Actions и required checks ветки.
CI выполняет lockfile install → format/lint/typecheck → unit/integration → build → E2E → preview/staging smoke; результаты связаны с одним commit SHA.
Нужны отдельные тестовые deployments, минимальные permissions workflow, управляемые secrets и запрет запуска недоверенного PR-кода с production credentials.
Порог coverage выбирается по риску: все существенные ветви авторизации и согласий должны иметь проверки; процент строк сам по себе не доказывает безопасность.

## 10. Релиз и откат

Поток: **PR → проверки → preview → staging → неизменяемый artifact с выключенным флагом → сотрудники → 1% → 5% → 25% → 100%**.
Проценты и интервалы — шаблон; владелец задаёт их по достаточному объёму событий и риску конкретной функции.
Release manifest связывает frontend/SSR artifact, Convex deployment, schema compatibility, migration state, source maps и release SHA.
Одновременно с выкладкой отправляется deployment marker; dashboard позволяет сопоставить изменения ошибок, latency, метрик и вариантов эксперимента.
При нарушении guardrails останавливается расширение аудитории и выключается флаг; предыдущий совместимый artifact хранится для восстановления.
Автоматический canary не гарантирует обнаружение регрессии при малом трафике; нужны ручной kill switch, smoke checks и владелец решения.
Миграции используют **expand → backfill → switch → contract**; удаление старой схемы откладывается до конца окна отката.
Rollback приложения и отключение флага **не отменяют данные, внешние действия или уже собранные согласия**. Исправление данных оформляется отдельной контролируемой операцией.
PWA/service worker обновляется с проверкой совместимости старого клиента и нового backend; активные операции пользователя не обрываются принудительным обновлением.
После завершения эксперимента сохраняются гипотеза, параметры и результат, удаляется временный код и архивируется флаг.

## 11. Условия готовности первого эксплуатационного пилота

- Для Datadog подтверждены регион, функции, retention, стоимость и доступ ответственных.
- Один desktop и один mobile сценарий связываются с release, безопасными событиями, ошибкой и доступной серверной диагностикой.
- Canary с чувствительным текстом не обнаруживается в telemetry; replay клинических страниц выключен.
- Потеря exporter и повторная доставка не ломают приложение; drops, backlog и дедупликация наблюдаемы.
- Для выбранного audit-контура доказаны запись, доставка, повторная выдача/cache hit, отказ и контроль доступа к журналу.
- Откат флага, возврат совместимого artifact и восстановление из резервной копии отрепетированы раздельно.
- Критические SLI имеют baseline, согласованные пороги, ответственного и проверенный runbook; итог пилота сохраняется как evidence.
