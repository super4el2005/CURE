# План реализации CURE

Дата: **28 октября 2026 года**. Это план нового приложения. Код, внешние сервисы, релизы и проверки ниже ещё не выполнены.

## 1. Очерёдность

```text
E0 Совместимость и ключевые решения
 ↓
E1 Общая база, аккаунты и рабочая версия на синтетических данных
 ↓
E2 Интеграции, качество и первый контролируемый клинический источник
 ↓
E3 Согласия, кабинет пациента и многоцентровая работа
 ↓
E4 Проведение исследования и безопасность участников
 ↓
E5 Воспроизводимая аналитика и AI-отчёты
 ↓
E6 Регионы, федерация, партнёрства и финансирование
```

i18n, два типа интерфейса, стандартные темы, контроль доступа, аудит, CI и наблюдаемость начинаются в E1 и развиваются на каждом этапе. Согласия имеют минимальный обязательный вариант в E1–E2 и полноценный процесс в E3. Поэтому ранняя интеграция не получает свободного доступа к реальным медицинским данным.

Сроки ниже — ориентиры для планирования, не обязательство: постоянная команда 4–6 инженеров с QA, дизайнером и доступными клиническим экспертом, биостатистиком и ответственным за данные. Время внешних согласований, подключения МИС, закупок и валидации может определять критический путь. Точность повышается после E0 и выбора первого источника; полное покрытие требований — программа на многие месяцы, не один MVP-спринт.

## 2. E0 — доказать совместимость, 1–2 недели

Результат: минимальный технический прототип и короткие записи решений. Он не должен разрастаться в продукт до устранения блокеров.

| Проверка | Что считается успехом |
|---|---|
| Start + Rsbuild 2/Rspack + Mantine | Production build и запуск SSR; стили загружаются; прямое открытие URL работает |
| Плоские маршруты desktop/mobile | Разные страницы отдаются сервером; cookie override работает; hydration не меняет вариант |
| Auth | Принято явное решение Convex Auth / Better Auth / IdP; вход, refresh, logout, отзыв и MFA проходят на серверном маршруте |
| Граница сборки auth | SSR adapter и зависимости корректно собираются Rsbuild; серверные секреты не попадают в client bundle |
| Convex + Query SSR | Два параллельных запроса разных пользователей/организаций не смешивают кэш или токены |
| TanStack DB | Изменение из второй вкладки обновляет нужную коллекцию; rollback/conflict не оставляет ложное сохранение |
| Persistence/outbox | Разрешённый черновик и операция переживают перезапуск; replay с тем же ключом не дублирует действие |
| i18n/тема | RU/EN на параллельных SSR-запросах; одинаковая гидратация языка/дат; штатная тема без flash-проблем |
| Тестовый стек | Rstest для доменной логики; реальные Convex integration tests; проверена возможность использования convex-test без неподтверждённой зависимости от Vitest |
| Наблюдаемость | Тестовая ошибка browser → SSR → Convex видна с release/operation ID в пределах доступных интеграций; демонстрация SLO/flags/experiment |
| Аудит/регион | Выбран поддерживаемый регион и способ надёжного аудита; понятны стоимость и ограничения тарифа |

Выход E0: lockfile с точными совместимыми версиями; ADR по auth, аудиту, локальному хранению, региону и Datadog; список подтверждённых API и оставшихся ограничений. До реализации нужно выбрать первые страны, пилотную клинику/университет и источник данных. Это продуктовые входные данные, а не повод останавливать подготовку архитектуры.

## 3. E1 — общая база и аккаунты, 4–6 недель

Вертикальный сценарий: человек регистрируется → подтверждает аккаунт и настраивает MFA → создаёт организацию или принимает приглашение → входит в команду → создаёт исследование → формирует когорту по синтетическим данным → запрашивает доступ → уполномоченный участник рассматривает заявку → разрешённый экспорт появляется в журнале.

В этап входят все функции описанной демоверсии: 10 000 синтетических пациентов, согласованные стартовые роли, фильтры, исследования, когорты, заявки на доступ, базовые согласия, CSV, базовая аналитика, каталог организаций и журнал действий. Каждая функция работает с общей серверной БД, а не только с локальным массивом.

Основа интерфейса: по одному файлу на маршрут; desktop/mobile варианты; стандартный Mantine; RU/EN; light/dark/system. PWA устанавливается и показывает безопасный offline fallback. Локальное хранение ограничено выбранными нечувствительными черновиками.

Основа эксплуатации: GitHub Actions, нативные hooks, conventions, lint/format/typecheck, Rstest, Playwright для критических сценариев, preview/staging, централизованные telemetry/events, feature flag и ручной проверенный откат. С первого этапа доступны минимальный отзыв согласия/grant и проверка expiry; развитый пациентский и этический процесс добавляется в E3.

Критерии приёмки:

- Два участника разных браузеров видят общее состояние; сервер отвергает попытку доступа к чужой организации даже при подмене ID.
- Отозванные сессия, membership и grant перестают открывать защищённый ресурс; прямой URL не обходит проверку.
- MFA нельзя обойти прямым вызовом чувствительной серверной операции; приглашение нельзя использовать повторно или для другого адресата.
- CSV содержит только разрешённые строки/поля; формульные значения безопасно экспортируются для открытия в таблицах.
- SSR-кэши изолированы, смена аккаунта не оставляет данные предыдущего; service worker не сохраняет персонализированные ответы.
- В продуктовой аналитике нет медицинских значений/текстов/токенов; подтверждённая бизнес-операция не считается дважды из-за повтора запроса.
- Для заявленного объёма измерены p95/p99, расход запросов/подписок, объём браузерной памяти; массовая загрузка всех записей не требуется.
- CI блокирует нарушения, команда демонстрирует отключение новой функции и возврат предыдущего артефакта.

Граница этапа: пригодная к проверке совместная платформа на синтетических данных. Наличие этих экранов не даёт автоматического разрешения на реальную клиническую эксплуатацию.

## 4. E2 — интеграции и качество, 4–8 недель

Первый согласованный клинический источник, один контракт/профиль обмена, CSV импорт, checkpoint/idempotency, provenance, карантин и отчёт о качестве. История заболеваний, лабораторные результаты и назначения — первая предметная область; изображения, геномика и биообразцы подключаются по реальной доступности источников, не одним универсальным полем JSON.

Критерии приёмки:

- Повторный импорт той же версии не создаёт дубли; частичный сбой возобновляется с проверенного checkpoint.
- Исходное значение и единица не теряются при нормализации; неподдерживаемая единица/код попадают в quarantine.
- Проверяются обязательность, диапазоны, временные противоречия, связи и вероятные дубли; сомнительное объединение подтверждается человеком.
- Доступ к реальным данным открывается только после проверки применимой цели/согласия, регионального контура и аудита.
- До первого импорта проверены отзыв согласия, expiry, открытая вкладка/reconnect и отмена ожидающего экспорта; после отзыва новые данные не выдаются. Отказ в доступе и отказ audit storage не обходят контролируемую выдачу.
- Качество и задержка источника измеряются; известно, какие записи не попали в когорту и почему.
- Медицинские файлы скачиваются через проверяемый доступ; постоянные публичные bearer-ссылки не выдаются.
- Выполнено тестовое восстановление базы, файлов и конфигурации с измеренными RPO/RTO; пересозданы ожидающие jobs и применены отзывы после snapshot. Восстановление не возвращает истёкшие/отозванные разрешения.

## 5. E3 — согласия, пациент и несколько центров, 6–10 недель

Версии протоколов/согласий, этическое рассмотрение, сроки и цели grants, повторное согласие, отзыв. Привязанный кабинет пациента: подходящие исследования, электронное согласие, дневник, версионированные опросники, календарь визитов и разрешённые результаты. Основной дневник сначала online; persistent offline для чувствительных записей требует отдельного решения.

Центры исследования получают собственные команды, задачи, сроки, цели набора и бюджет. Подбор участников исполняет inclusion/exclusion criteria с объяснением, неизвестными значениями, оценкой доступной выборки и врачебной проверкой.

Критерии приёмки:

- Два центра работают по согласованной версии протокола и видят только разрешённые данные и общие показатели.
- Изменение протокола показывает, где требуется принятие поправки и новое согласие.
- Отзыв согласия блокирует новые выдачи, прекращает применимые подписки и не допускает публикацию ожидающего экспорта.
- Срок grant работает без ручной уборки, включая открытую вкладку, reconnect и задержку scheduler; jobs повторно авторизуют действие перед внешним эффектом.
- По любому разрешению можно восстановить документ, версию, подписанта, решение комитета, цель и период.
- Пациент не может привязать чужую медицинскую запись одним знанием ID; врач подтверждает кандидата по объяснимым критериям.
- Напоминания о визитах учитывают timezone центра/пациента и переходы времени; разные языки не меняют смысл подписанного документа.

## 6. E4 — проведение и безопасность, 6–10 недель

eCRF, версии и валидация форм, запросы уточнений, визиты, фиксация данных, отклонения, отдельно рандомизация/ослепление. Нежелательные события: оценка, ответственный, доставка уведомления, подтверждение, эскалация, история решения.

Критерии приёмки:

- Параллельные команды не распределяют участника дважды; скрытая группа недоступна через API, экспорт и логи.
- Экстренное раскрытие проходит отдельное полномочие, причину и аудит.
- Исправление зафиксированной формы сохраняет прежнюю версию, причину и автора; обязательные проверки нельзя обойти API-вызовом.
- Просроченное рассмотрение события приводит к эскалации; отказ канала уведомлений виден и повторяется контролируемо.
- Клинический владелец утверждает сценарии валидации для выбранного типа исследования.

Если пилот включает интервенционное исследование, относящиеся к нему функции безопасности и их валидация становятся условием запуска такого пилота. Порядок дорожной карты не позволяет проводить его без необходимых процессов до E4.

## 7. E5 — научная аналитика и AI-отчёты, 6–10 недель

Сравнение когорт, расчёт размера выборки, модели, пропуски/смещения, планы анализа, версии наборов и воспроизводимые R/Python jobs. AI формирует проверяемую спецификацию Mantine-отчёта и объяснение, использует разрешённые инструменты и сохраняет версию с параметрами. Sharing ограничен получателем, сроком и его собственными правами.

Критерии приёмки:

- Один снимок, код, окружение и параметры воспроизводят результат в оговорённой численной точности.
- Результаты проверены на эталонных наборах и рецензированы биостатистиком; отображаются метод и допущения.
- LLM не исполняет произвольный код, не расширяет grants и не получает неразрешённые исходные записи.
- В отчёте прослеживается каждая таблица/цифра до разрешённого расчёта и версии данных.
- Отзыв/истечение share grant блокирует новую выдачу; recipient не наследует полномочия автора.
- Подделка tool arguments и инструкции в загруженном документе не обходят серверную политику.
- Основные сценарии работают без WebMCP; его поддержка проверяется отдельно.

## 8. E6 — международное расширение и наука

Региональные deployment и хранилища, версия политики страны, международные форматы обмена, федеративный анализ, дополнительные языки. Каталог партнёров/экспертов, исследовательских запросов, грантов, заявок и результатов, учёт вклада организаций и авторства.

Этот этап оценивается отдельно после выбора стран, юридических контуров и партнёров; надёжного общего срока сейчас нет. Для каждой новой страны проверяются данные, auth, telemetry, AI, резервные копии и межрегиональные обмены.

Критерии приёмки: исходные записи остаются в заданном регионе; недопустимый перенос отклоняется; один пакет анализа запускается в двух клиниках и возвращает сопоставимые разрешённые агрегаты; публикация имеет версии, разрешение, вклад участников и источники. Размещение в регионе само по себе не доказывает соответствие всем требованиям страны.

## 10. Первые поставляемые изменения после решения начать код

1. Воспроизводимый toolchain и CI, минимальные SSR desktop/mobile страницы на стандартном Mantine.
2. Проверенный auth flow с серверным SSR, MFA и изоляцией двух организаций.
3. Convex schema, membership/invitation/access rules и синтетический seed.
4. Исследование → когорта → заявка → grant → контролируемый экспорт → аудит.
5. Разрешённый офлайн-черновик, смена аккаунта, централизованная telemetry и проверенный откат.

Каждое изменение должно быть завершённым вертикальным сценарием с проверкой серверных границ. Рисовать сразу 22 раздела меню с заглушками не считается выполнением этапа.
